1. Resumen Ejecutivo y Justificación del Negocio

En las organizaciones contemporáneas de tecnología, la falta de un sistema formal y auditable para la gestión de incidentes operativos genera una severa degradación en la continuidad del negocio. El uso informal de canales como mensajería instantánea o llamadas telefónicas deriva en pérdidas de contexto, ausencia de métricas de rendimiento (MTTR) y nula rendición de cuentas ante fallas críticas.

IT Incident Hub es una plataforma de grado industrial diseñada para resolver de raíz este problema, integrando la gestión operativa de incidentes con una infraestructura de aseguramiento de calidad continua basada en los paradigmas modernos de DevOps y Site Reliability Engineering (SRE).

7. Gestión de Deuda Técnica y Auditoría de Vulnerabilidades OWASP

Siguiendo las directrices de la rúbrica y los estándares de producción empresarial (OWASP Top 10), se identificaron y documentaron formalmente 5 deudas técnicas estructurales en docs/deuda_tecnica.md, además de ejecutar una auditoría exhaustiva de ciberseguridad y arquitectura sobre las 6 dimensiones del proyecto, aplicando todas las remediaciones directamente en el código fuente:

7.1 Catálogo de Deuda Técnica Identificada y Mitigada

ID Severidad Deuda / Debilidad Identificada Por qué era un Riesgo Cómo se Solucionó en Código
DT-1 [CRÍTICO] Ausencia de escapado HTML en plantillas SMTP, renderizado dangerouslySetInnerHTML y cabeceras HTTP. Permitía inyección de código malicioso Stored XSS (OWASP A03) al visualizar correos o descripciones con payloads <img onerror=...>. RESUELTA • Función escapeHtml() en securityMiddleware.js, escapado en emailService.js y <iframe sandbox=""> en DevOpsMonitor.jsx (AB#27).
DT-2 [ALTO] Manejador de errores, validadores y servicios desconectados del servidor Express (Split-Brain Architecture). Enviar tipos no string (ej. {"category": 123}) causaba TypeError no capturados y fugas de stacktrace en respuestas 500. RESUELTA • Conexión real de validateCreateIncident, asyncHandler y errorHandlerMiddleware en backend/server.js (AB#27).
DT-3 [ALTO] Falta de índices compuestos en PostgreSQL y consultas SQL transaccionales reales en db.js. Degradación en filtros multicriterio y ausencia de persistencia ACID real cuando PostgreSQL está activo. RESUELTA • Índice compuesto idx_incidents_multicriteria en schema.sql y CRUD SQL parametrizado con BEGIN/COMMIT/ROLLBACK en db.js (ADR-004).
DT-4 [CRÍTICO] Exposición de accessCode en /api/users, login sin contraseña y ausencia de RBAC/Rate Limiting en API. Permitía suplantación de identidad (OWASP A01/A07) y ataques de fuerza bruta o denegación de servicio (DoS). RESUELTA • Proyección toPublicUser(), tokens firmados HMAC-SHA256, middleware requireAdminRole y createRateLimiter en securityMiddleware.js.
DT-5 [ALTO] Pruebas unitarias aisladas sin ejercitar el servidor HTTP Express ni la máquina de estados completa. Regresiones en rutas HTTP, cabeceras de seguridad o saltos de estado ilegales (NUEVO ➔ CERRADO) pasaban desapercibidas. RESUELTA • Grafo estricto ALLOWED_TRANSITIONS en workflowService.js y Subtest 8 de integración HTTP real sobre Express en tests/api.test.js.

7.2 Matriz Completa de Vulnerabilidades Auditadas y Remediadas (Estándar Producción)

Cód. Clasificación Vulnerabilidad / Debilidad Detectada Por qué era un Riesgo Remediación Aplicada en el Proyecto
C1 [CRÍTICO] Broken Access Control y Fuga de Credenciales (OWASP A01/A02): GET /api/users devolvía accessCode en texto claro y POST /api/auth/login aceptaba {userId: 1} sin clave. Cualquier visitante podía leer las claves de todos los operadores en red y tomar control total del rol ADMIN sin autenticarse. Se implementó toPublicUser() para eliminar accessCode de toda respuesta JSON, se exigió validación constante con verifyAuthToken (HMAC-SHA256 + crypto.timingSafeEqual) y se protegió la API con requireAdminRole (HTTP 403).
C2 [CRÍTICO] Stored XSS e Inyección de Cabeceras SMTP (OWASP A03): emailService.js concatenaba campos sin escapar y DevOpsMonitor.jsx usaba dangerouslySetInnerHTML. Un atacante podía inyectar JavaScript arbitrario en el título de un ticket que se ejecutaba en el navegador del administrador al abrir el monitor DevOps. Se aplicó escapeHtml() a cada campo interpolado en buildEmailHtml y buildPipelineEmailHtml, limpieza de saltos \r\n (CRLF) en cabeceras SMTP y aislamiento mediante <iframe sandbox="" srcDoc={...} /> en React.
C3 [CRÍTICO] Secretos Hardcodeados en Infraestructura (Regla 9): Contraseñas por defecto en db.js, docker-compose.yml y token de ejemplo en guía HTML. Comprometía la infraestructura local/contenedorizada y violaba la Regla 9 de cero exposición de credenciales en el repositorio. 10. Flujo Dual de Calidad con GitHub Actions

Para robustecer el aseguramiento de la calidad, el equipo implementó una estrategia de Integración Continua Dual (Dual CI). Mientras Azure Pipelines gestiona la compilación de producción y artefactos en el agente local, GitHub Actions valida de forma complementaria cada Pull Request antes de su integración a main:

10.1 Definición del Workflow Complementario (.github/workflows/ci.yml)

name: CI Pull Request Validation
on:
  pull_request:
    branches: [ main ]
  push:
    branches: [ main ]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - name: 1. Checkout de Código Fuente
        uses: actions/checkout@v4

      - name: 2. Configurar Entorno Node.js 20.x
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: 3. Restaurar Dependencias Backend (Determinístico)
        run: cd backend && npm ci --no-audit

      - name: 4. Auditoría de Seguridad SCA (npm audit)
        run: cd backend && npm audit --audit-level=high

      - name: 5. Ejecutar Suite de Pruebas Unitarias e Integración HTTP
        run: node --test tests/api.test.js
Ventajas de la Arquitectura Dual CI
1. Doble barrera de protección: Ningún PR puede integrarse sin superar el workflow de GitHub Actions en la nube.
2. Neutralidad de plataforma: El código es validado tanto en contenedores Linux (Ubuntu en GitHub Actions) como en Windows nativo (Self-Hosted Agent en Azure Pipelines).

18. Conclusiones y Recomendaciones de Ingeniería

18.1 Conclusiones de Ingeniería

  1. Madurez DevOps e Integración Continua Real: El proyecto evidenció que la adopción rigurosa de una cultura de integración continua trasciende el desarrollo tradicional. Al implementar un agente autohospedado local que ejecuta compilaciones reales de Vite, validación de dependencias SCA (0 vulnerabilidades) y ejecución de pruebas nativas, se garantiza que ningún código defectuoso alcance entornos productivos.
  2. Trazabilidad Holística Bidireccional: La articulación estricta entre Azure Boards (Work Items AB#4 a AB#34), ramas temáticas de Git y commits referenciados elimina cualquier incertidumbre sobre el origen y propósito de cada modificación, estableciendo una cadena de custodia inmutable desde el requerimiento del negocio hasta el artefacto compilado.
  3. DevSecOps y Seguridad por Diseño (Regla 9): La erradicación de secretos en código fuente, la protección de remotos Git, el uso de Variable Groups bajo candado cerrado y la sanitización de entradas contra XSS demuestran que la seguridad es un pilar arquitectónico no negociable en sistemas modernos.
  4. Resiliencia de Persistencia y Continuidad Operativa: El patrón de persistencia dual documentado en ADR-004 garantiza compatibilidad con bases de datos relacionales empresariales (PostgreSQL 16) y asegura a la vez la continuidad operativa en entornos efímeros de pruebas automatizadas.

18.2 Recomendaciones Futuras

  1. Implementación de Pruebas de Carga y E2E: Incorporar herramientas de automatización de pruebas de extremo a extremo en navegador real (Playwright o Cypress) dentro del workflow de GitHub Actions para evaluar la experiencia de usuario sintética en cada Pull Request.
  2. Orquestación de Contenedores y Kubernetes: Para hitos posteriores (v2.0.0), empaquetar el backend y la base de datos en imágenes OCI mediante Dockerfiles multi-stage y orquestar su despliegue mediante Helm Charts en Azure Kubernetes Service (AKS).
  3. Monitoreo de Telemetría Distribuida (APM): Integrar OpenTelemetry o Azure Application Insights para capturar trazas distribuidas, perfiles de consumo de memoria y métricas de latencia de endpoints en tiempo real.
