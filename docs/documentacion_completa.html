1. Resumen Ejecutivo y Justificación del Negocio

En los entornos corporativos modernos de infraestructura y soporte de tecnologías de la información, la atención dispersa de fallas técnicas mediante canales informales —tales como llamadas telefónicas, mensajería instantánea y correos electrónicos no estructurados— representa una pérdida crítica de trazabilidad, incrementa drásticamente los Tiempos Medios de Reparación (MTTR) y genera islas de información imposibles de auditar.

El proyecto integrador IT Incident Hub nace con el objetivo de erradicar esta problemática mediante el diseño, construcción y despliegue continuo de una solución web integral y trazable, alineada con las mejores prácticas de la cultura DevOps. La solución sustituye los reportes volátiles por una plataforma web con observabilidad completa de punta a punta: desde la necesidad del negocio registrada en Azure Boards, el versionamiento y revisión por pares en GitHub, la validación automatizada en Azure Pipelines y GitHub Actions, hasta la generación de artefactos inmutables de producción bajo Versionado Semántico (SemVer).

🎯 Meta Cuantitativa y Cualitativa Alcanzada
El proyecto superó las métricas exigidas en la rúbrica de evaluación: 3 semanas incrementales de ingeniería, 3 repositorios oficiales vinculados (Semana 1 Base, Semana 2 Calidad/Seguridad y Semana 3 Release), 30 Work Items en Azure Boards (2 Epics, 4 Features, 8 User Stories y 16 Tasks) cerrados al 100%, 13 Pull Requests reales con code reviews, suite de 8 pruebas unitarias pasando en verde y cero vulnerabilidades de seguridad reportadas en dependencias.

4. Gestión de Ramas Git y Trazabilidad de Commits

Para garantizar la estabilidad absoluta de la rama main y evitar conflictos en despliegue, el equipo adoptó una adaptación rigurosa de GitFlow. Todo cambio de código inició obligatoriamente en una rama secundaria estructurada bajo convención:

  • feature/*: Para incorporación de nuevas funcionalidades de negocio (ej. feature/incident-crud, feature/incident-filters).
  • refactor/*: Para resolución de deuda técnica y refactorizaciones (ej. refactor/xss-sanitization-dt1, refactor/error-handling-dt2).
  • fix/*: Para resolución de fallos y bugs identificados en integración (ej. fix/controlled-pipeline-failure).
  • release/*: Para estabilización previa al versionamiento semántico.

4.1 Trazabilidad Obligatoria con Work Items (AB#ID)

Cada confirmación de código (commit) incluye estrictamente la referencia numérica de su Work Item correspondiente en Azure Boards. Esto permite que Azure Repos y GitHub sincronicen los cambios bidireccionalmente: 

# Flujo Trazable de Ingeniería:
Task Técnica en Boards (AB#27) ──> Rama refactor/xss-sanitization-dt1 ──> Commit "fix: Sanitización XSS en endpoints AB#27" ──> PR #1 revisado ──> Merge en main

8. Workflow Complementario en GitHub Actions

Como estrategia de aseguramiento de calidad de doble vía (Dual CI), se implementó un flujo de trabajo complementario en .github/workflows/ci.yml para ejecutar auditoría de seguridad y pruebas unitarias automáticas ante cada apertura o actualización de Pull Requests hacia main: 

name: CI Pull Request Validation
on:
  pull_request:
    branches: [ main ]
  push:
    branches: [ main ]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - name: Restaurar dependencias Backend
        run: cd backend && npm install --no-audit
      - name: Auditoría de Seguridad SCA (npm audit)
        run: cd backend && npm audit --audit-level=high
      - name: Suite de Pruebas Unitarias Automatizadas
        run: node --test tests/api.test.js

14. Conclusiones y Recomendaciones de Ingeniería DevOps

  1. Trazabilidad Integral como Pilar de Confiabilidad: La articulación estricta entre Azure Boards, ramas especializadas de Git y commits referenciados con AB#ID erradica por completo la ambigüedad en el origen de los cambios, garantizando que cada línea de código responda a un requerimiento de negocio medible.
  2. Cultura de Doble Validación (Dual CI): La orquestación paralela entre Azure Pipelines (ejecutando en un agente autohospedado local con build de producción real) y GitHub Actions (validando de forma inmediata en la nube cada Pull Request) minimiza el riesgo de introducir regresiones a la rama main, logrando un ciclo de integración ágil y robusto.
  3. Seguridad por Diseño (DevSecOps) y Cero Secretos: La eliminación de tokens PAT en configuraciones locales, el uso de Variable Groups protegidos bajo candado cerrado y la verificación automatizada de dependencias con npm audit demuestran que la seguridad no es un paso tardío, sino un control inmutable embebido en el pipeline de ingeniería.
  4. Resiliencia de Persistencia y Continuidad Operativa: La implementación del adaptador dual documentado en ADR-004 garantiza que la plataforma cumpla con los estándares de bases de datos relacionales empresariales (PostgreSQL 16) y al mismo tiempo mantenga su alta disponibilidad en entornos efímeros de pruebas automatizadas.
